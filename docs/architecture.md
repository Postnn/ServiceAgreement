# Архитектура ServiceAgreement

Подготовка к возможному переносу на Clayzor. Целевой интерфейс — **обычный ClayGrid
с заданным SQL-запросом**, не Dynamic ClayGrid. На этом этапе приложение остаётся
Windows standalone, схема БД, пользовательские SQL и формат config.json сохранены.

## Границы пакетов

- `domain`: Record, Option, XDD, нормализация точной суммы, проверка договора и
  ErrConflict. Не зависит от БД, файлов конфигурации и Windows.
- `service`: Agreements и интерфейс Repository. Прикладные операции проверяют
  команду, вызывают хранилище и возвращают Mutation только после успешной записи.
  Не загружают списки повторно и не управляют окнами.
- `readmodel`: ListResult, исходные значения строк, ColumnMetadata и описание
  колонок. Никаких подключений к БД или Windows-контролов.
- `sqlserver`: выполнение параметризованных запросов, общий scanner обоих списков,
  чтение метаданных, проверка конкурентного обновления.
- `sqlquery`: существующие разбор и композиция SQL, поиск и порядок сортировки.
- `config`: прежний JSON-контракт, SQL по умолчанию, миграция старой конфигурации,
  файловое сохранение и настройка времени ожидания.
- `presentation`: форматирование, локальная сортировка и фильтры, согласование
  колонок. PrepareList формирует отображение из исходных значений результата.
- `cmd/serviceagreement`: окна Walk, жизненный цикл подключения и адаптация
  результата сервиса к интерфейсу.

Окна вызывают сервис для CRUD, списков и справочников. Операции настройки
подключения/SQL-схемы остаются в инфраструктурном коде настройки приложения.
Конкретный Store связывается с сервисом только при сборке зависимостей в UI;
service не импортирует sqlserver, config, presentation или Windows.

## Данные и отображение

Оба списка возвращают `ListResult`: `Columns` + `Items`. ColumnMetadata содержит
имя, SQL-тип, Nullable, Precision и Scale, с признаками доступности метаданных.
Даже при нуле строк интерфейс знает типы колонок. Драйвер не обязан предоставлять
все свойства: флаг Known=false не означает NOT NULL или масштаб 0.

Хранилище заполняет только исходные Raw-значения. PrepareList создаёт Values для
отображения и сохраняет Raw. Существующие локальные фильтры используют проекцию
ColumnTypes в строках; для пустого результата UI обращается к Columns результата.
Числовые типы выравниваются вправо, N2 применяется исключительно к SQL MONEY.

Обычное ручное обновление сохраняет прежнее согласование структуры SELECT и
подтверждение удаления настроек исчезнувших колонок. После записи дополнительная
проверка SQL-схемы не запускается. Объединение ручной проверки схемы с загрузкой
данных возможно отдельным изменением поведения; в этот рефакторинг не входит.

## Результат записи

| Mutation | Список с параметрами | Список без параметров |
|---|---:|---:|
| Updated | 1 загрузка | 0 |
| Inserted / Deleted | 1 загрузка | 1 загрузка |
| None (ошибка/отмена) | 0 | 0 |

Политикой обновления управляет UI. Конкурентное обновление, SQL-параметры и точная
исходная сумма сохранены. Удаление пока использует прежнюю проверку по ID.

## Переносимые примеры

`testdata/contracts/xdd.json` и `money.json` — общий контракт версии 1.
Тесты `internal/contracts` исполняют эти файлы. Будущие C#-тесты должны читать те
же файлы, не пересоздавая ожидаемые ответы своим алгоритмом.

- Даты: ISO yyyy-MM-dd, календарные даты без часового пояса/времени.
- `error: true`: операция должна отклонить вход; текст ошибки не является контрактом.
- Код XDD: JSON-целое; для проверки выхода за Int32 C#-тест сначала читает Int64.
- Суммы: десятичные строки, не JSON float. SQL money имеет четыре дробных знака.
- N2: запятая, два дробных знака, разделитель тысяч U+00A0, округление midpoint-to-even.
- `display.input: null` означает SQL NULL, а не пустую строку.
- Неизменённое отображение N2 сохраняет точное первоначальное значение money.
- Примеры XDD иллюстрируют относительный срок, не определяют оплату/задолженность.

Проверки: `go test ./...`, `go vet ./...` на Windows; независимые пакеты проверяются
также на Linux. Windows CI собирает ZIP через существующий workflow на pull request.

## Последующий web-этап

Перенос правил в C# с проверкой по этим fixtures; обычный ClayGrid, ClayEditForm и
ClayComboBox. SQL-операции адаптируются к Clayzor DALC и его требованиям.
Серверная пагинация/фильтрация, права пользователя и серверная конфигурация —
отдельный этап. Ни Go HTTP API, ни Dynamic ClayGrid здесь не добавляются.
