# ServiceAgreement — параметры договоров оказания услуг

Минималистичное графическое Windows 10/11 x64 приложение на Go (Win32/Walk).
Предназначено для редактирования `dbo.[ДокументыДоговораОказанияУслуг]` в Microsoft SQL Server.
Не требует установленного Go, .NET, ODBC-драйвера или запуска собственного сервера.

## Быстрый запуск

1. Скачайте `ServiceAgreement-windows-amd64.zip` из последнего GitHub Release.
2. Распакуйте в папку с правом записи (для изменения настроек понадобится запись в `config.json`).
3. Запустите `ServiceAgreement.exe` и нажмите значок **⚙** в правом верхнем углу главного окна (подсказка «Настройки SQL и колонок»). Введите строку подключения к SQL Server.
4. В окне настроек можно проверить соединение, исправить SQL-запросы и настроить колонки. Нажмите «Сохранить».
5. Выберите договор в списке, дважды щёлкните или нажмите «Изменить».

Рядом с EXE находится `config.json` (образец — `config.example.json`). Если конфигурации нет или БД недоступна, основное окно всё равно открывается: можно зайти в настройки, не редактируя JSON вручную.
Изменения в конфигурации применяются сразу; при сохранении существующий `config.json` копируется в `config.json.bak`. Не публикуйте реальные конфигурации с секретами в GitHub.

## Главное окно

Кнопка **⚙** располагается в правом верхнем углу главного окна, доступна на обеих вкладках и по наведению показывает подсказку «Настройки SQL и колонок». Прежняя текстовая кнопка внизу окна удалена.

Два независимых списка в отдельных вкладках:

1. **Договоры с параметрами** — прежняя таблица и поиск по одному `list_sql`, с добавлением, изменением и удалением параметров.
2. **Договоры без параметров** — отдельный список, полностью управляемый запросом `without_parameters_sql`. Поле поиска работает по Enter и кнопке «Найти»; каждое слово поиска передаётся отдельным параметром `@SearchText1`, `@SearchText2` и т. д. Двойной щелчок или кнопка **«Задать параметры»** открывает форму добавления с уже выбранным и заблокированным от изменения договором. Название берётся из поля `Договор` результата (также поддерживается прежний алиас `ContractName`). После успешного сохранения запись перемещается в список с параметрами; **обе таблицы обновляются автоматически**, сохраняя текущие фильтры.

**Во втором списке отображаются все пользовательские поля из SELECT, кроме служебных `ContractID` и `SearchText`.** Настройки `list_columns` для второго списка не требуются. Имя алиаса SQL — заголовок колонки. Обязательный алиас `ContractID` (положительное целое число) позволяет открыть именно нужный договор. Другие алиасы и их порядок определяет только запрос, включая случай, когда запрос вернул ноль строк. Лимит количества записей — общий `list_limit`.

### Единый поиск по SearchText

В настройках хранятся **два SQL-запроса списка**: `list_sql` для договоров с параметрами и `without_parameters_sql` для договоров без параметров. Отдельного `search_sql` больше нет. Каждый из двух запросов должен возвращать `ContractID` и **`SearchText`**.

При нажатии Enter или кнопки «Найти» пользовательская строка делится по пробелам, табуляции и переносам на слова. Приложение оборачивает соответствующий запрос в `SELECT TOP (@limit) ... FROM (<исходный SQL>) AS [Source]`, затем добавляет по одному условию на слово, **объединяя их через AND**:

```sql
SELECT TOP (@limit) [Source].*
FROM (
    -- SELECT, заданный в list_sql или without_parameters_sql
) AS [Source]
WHERE (N'   ' + COALESCE(CONVERT(nvarchar(max), [Source].[SearchText]), N'')
       LIKE N'% ' + @SearchText1 + N'%' ESCAPE N'~')
  AND (N'   ' + COALESCE(CONVERT(nvarchar(max), [Source].[SearchText]), N'')
       LIKE N'% ' + @SearchText2 + N'%' ESCAPE N'~')
ORDER BY [Source].[ContractID] DESC
```

Число параметров зависит от числа введённых слов. **Все слова должны присутствовать** в `SearchText` (по началу слов, как в формуле с пробелом). Значения параметризованы, спецсимволы SQL `LIKE` экранируются. При пустом поиске внешний `WHERE` не создаётся.

**Важно:** исходные `list_sql` и `without_parameters_sql` могут начинаться с `SELECT`, `;WITH` или `WITH`. Их **итоговый SELECT** должен быть пригоден для подзапроса, без предварительного `TOP` и завершающего `ORDER BY`. Ограничение `TOP (@limit)` и сортировка по `ContractID` выполняются внешним запросом **после фильтрации**. Штатные старые запросы приложение обновляет автоматически, если они не были изменены пользователем. Пользовательские запросы не переписываются: при необходимости удалите в них `TOP` и `ORDER BY` и добавьте `SearchText`.

### Поддержка CTE в исходных SQL-запросах

Оба запроса списка могут начинаться с **`SELECT`**, **`;WITH`** или **`WITH`**. Например, настройка `list_sql` может содержать:

```sql
;WITH Договоры AS (
    SELECT t.[КодДокументаДоговораОказанияУслуг] AS ContractID,
           d.[Договор] AS Договор,
           CONCAT(t.[КодДокументаДоговораОказанияУслуг], N' ',
                  d.[Договор]) AS SearchText
    FROM dbo.[ДокументыДоговораОказанияУслуг] AS t
    JOIN dbo.[ДокументыДанные] AS d
      ON d.[КодДокумента] = t.[КодДокументаДоговораОказанияУслуг]
)
SELECT ContractID, Договор, SearchText
FROM Договоры
```

SQL Server не позволяет помещать `;WITH ...` непосредственно внутрь `FROM (...)`. Поэтому приложение отделяет объявление **одного или нескольких CTE** и оставляет его перед внешним `SELECT TOP (@limit)`. Во внутреннем `FROM (...)` оказывается только заключительный `SELECT`, обращающийся к CTE. Комментарии, текстовые литералы и исходные отступы не меняются.

Правила для **заключительного SELECT** остаются прежними: он должен возвращать `ContractID` и `SearchText` и не должен содержать предварительный `TOP` или завершающий `ORDER BY`. Внутри определения CTE могут встречаться вложенные `SELECT`, `TOP` и `ORDER BY`, если они корректны с точки зрения T-SQL; помните, что ограничивающий `TOP` внутри самого CTE сокращает кандидатов для последующего поиска.

### Договоры без параметров

В `without_parameters_sql` применяется `NOT EXISTS`, исключающий договоры, которые уже имеют запись в `dbo.[ДокументыДоговораОказанияУслуг]`. Поле `dbo.[ДокументыДанные].[КодДокумента]` — идентификатор, `[Договор]` — готовое текстовое представление (тип, номер, дата).

Пример базового запроса:

```sql
SELECT
    d.[КодДокумента] AS ContractID,
    d.[Договор] AS [Договор],
    CONCAT(CONVERT(nvarchar(30), d.[КодДокумента]),
           N' ', CONVERT(nvarchar(max), d.[Договор])) AS SearchText
FROM dbo.[ДокументыДанные] AS d
WHERE NOT EXISTS (
    SELECT 1
    FROM dbo.[ДокументыДоговораОказанияУслуг] AS p
    WHERE p.[КодДокументаДоговораОказанияУслуг] = d.[КодДокумента]
)
```

Второй список выводит все колонки SQL, **кроме `ContractID` и `SearchText`**. Основной список управляет видимостью остальных полей через `list_columns`; служебные поля скрыты независимо от значения `visible`. Чтобы фильтровать только документы конкретного вида «договор оказания услуг», дополните исходный SQL критерием типа документа: точный идентификатор типа пока не задан.

Список с параметрами получает `AgreementLabel` из `ДокументыДанные.Договор` через `LEFT JOIN`, а `SearchText` содержит и код, и название.

- **Поиск по договору**: введите слова и нажмите **Enter** или кнопку **«Найти»**. Пустая строка показывает обычный список. «Обновить» повторяет поиск без его изменения.
- **Структура колонок основного списка** определяется **только `list_sql`** (даже при нуле строк). Новые SQL-алиасы автоматически добавляются в `list_columns` видимыми по умолчанию. Удаление настроек исчезнувших полей требует подтверждения. Заголовок, ширина, порядок, `sortField` и видимость других колонок сохраняются.
- Раздел «Колонки списка…» позволяет настроить отображение основного списка без ручного добавления SQL-полей.

## Форма редактирования

Вместо четырёх полей поиска и выбора здесь **два поля**:

- **Договор** — редактируемый выпадающий список (изменение договора существующей записи запрещено).
- **Тип документа основания автооплаты** — редактируемый выпадающий список.

Введите код или часть названия прямо в поле и нажмите **Enter**. Если запрос найдёт **одно** совпадение, оно автоматически выбирается. Если совпадений несколько, открывается выпадающий список для выбора. При отсутствии совпадений показывается сообщение. До выбора действительного элемента произвольный текст не считается кодом и не может быть сохранён вместо выбранного значения. Можно также сразу выбирать значение из первоначального выпадающего списка.

Период оказания услуги выбирается из удобных вариантов «Один месяц (1)», «Три месяца (3)», «Двенадцать месяцев (12)» либо вводится вручную целым числом 1–255 (тип SQL `tinyint`). Три поля XDD остаются составными (направление, смещение по месяцам, число месяца или «Последний день (99)»). При редактировании показываются реальный код для хранения в `int` и **примерная**, не договорная дата для текущего года. Примерная дата рассчитывается только для подсказки в окне редактирования; в списке все вычисления выполняет SQL. `X99` означает последний день месяца, включая високосный февраль.

## Настройка таймаута выполнения SQL

Параметр `connection_timeout_seconds` в `config.json` задаёт максимальное время выполнения одной операции с SQL Server в секундах. Значение по умолчанию — **30 секунд**, допустимое значение — **от 1 до 3600 секунд**. На форме настроек это поле называется **«Таймаут выполнения SQL-запросов (сек.)»**.

```json
{
  "connection_timeout_seconds": 120
}
```

Пример показывает только один параметр; остальные настройки остаются в том же JSON-объекте. Таймаут применяется к получению обоих списков, поиску, справочникам, чтению/созданию/редактированию/удалению параметров, проверке SQL-метаданных и подключению. Если запрос превысит время, операция завершится ошибкой по таймауту. Старый `config.json` без этого поля автоматически получает значение 30 секунд, остальные его настройки не меняются.

## Все настраиваемые SQL-запросы

Все восемь запросов редактируются непосредственно в **«Настройки SQL и колонок…»**. При открытии, переключении запросов и вставке текста редактор **сохраняет исходное расположение SQL**: переносы строк, пустые строки, отступы, табуляцию и пробелы. Используется моноширинный шрифт Consolas. Только кнопка **«Форматировать SQL»** автоматически расставляет отступы и переносы по запросу пользователя. Форматирование не изменяет текст SQL-литералов, комментарии и имена в квадратных скобках. В JSON сохраняется тот SQL, который отображается в редакторе (без необходимости вручную экранировать переносы строк).

| Поле `config.json` | Назначение | Параметры и обязательный результат |
|---|---|---|
| `list_sql` | Договоры с параметрами | Результат: `ContractID`, `SearchText` и необходимые алиасы списка; **без `TOP` и завершающего `ORDER BY`** |
| `without_parameters_sql` | Договоры без параметров | Результат: `ContractID`, `SearchText` и произвольные отображаемые поля; **без `TOP` и завершающего `ORDER BY`** |
| `contracts_sql` | Выпадающий список договоров | вход: `@search`, `@selected`, `@limit`; возвращает код и название |
| `document_types_sql` | Выбор типа документа основания автооплаты | вход: `@search`, `@selected`, `@limit`; возвращает код и название |
| `get_sql` | Чтение записи | вход: `@id`; ровно 11 колонок по схеме |
| `insert_sql` | Добавление записи | `@id`, `@type`, `@period`, `@auto`, `@amount`, `@day`, `@month`, `@docs`, `@pay`, `@off`, `@notify` |
| `update_sql` | Обновление записи | все параметры добавления и соответствующие `@old_*` |
| `delete_sql` | Удаление записи | `@id` |

SQL команды передаются через именованные параметры драйвера: строка поиска, выбранный ID и содержимое полей не конкатенируются в SQL. Для запросов модификации используются `RowsAffected`: при UPDATE/DELETE ожидается ровно одна изменённая строка; иначе выводится ошибка конфликта/отсутствия.

`get_sql` должен вернуть в таком порядке: код договора; код типа документа основания автооплаты; период; автооплата; сумма (`nvarchar`/`decimal(19,4)` без округления в float); день/месяц начала; документы XDD; оплата XDD; отключение XDD; оповещение куратора.

**Важно:** для сохранения защиты от конкурентного изменения в `update_sql` рекомендуется оставлять условия `@old_*` из образца. Если заменить запрос на `UPDATE ... WHERE id=@id`, защита от перезаписи чужих изменений перестанет работать.

## Сортировка по умолчанию

В настройках для двух запросов выборки есть отдельное поле **«Сортировка по умолчанию (ORDER BY)»**. Примеры: `AgreementLabel ASC, Amount DESC` и `[Договор] ASC, ContractID DESC`. Значения сохраняются как `list_order_by` и `without_parameters_order_by`.

Сортировка добавляется **во внешний SELECT**, после формирования CTE (если он есть), но **до `TOP (@limit)`**. В исходном запросе нет необходимости писать `ORDER BY`. Допускаются только имена возвращаемых SQL-алиасов и необязательные `ASC`/`DESC`, перечисленные через запятую. Для имён с пробелами используйте квадратные скобки; произвольные выражения и команды отклоняются. Пустая строка соответствует `ContractID DESC`.

## Денежные значения (N2)

Колонки SQL Server типа `money` и `smallmoney` в обоих списках отображаются с **двумя десятичными знаками, десятичной запятой и разделителями тысяч** (например, `1 234 567,89`). Стандартная колонка `Amount`, возвращаемая старым примером как `nvarchar`, также приводится к N2. **Сортировка и запись в БД используют исходные значения SQL, а не округлённый текст.** В форме редактирования само поле суммы отображается в N2 (например, `1 234,56`) и принимает русскую запись с запятой и разделителями тысяч. **Если сумма не менялась, SQL money с исходной точностью до четырёх знаков сохраняется без округления**; при изменении сумма преобразуется обратно в точный SQL-формат.

## Курсор ожидания

На время выполнения запросов SQL Server (загрузка обоих списков, поиск, чтение, сохранение, удаление, выбор справочных значений, проверка структуры и проверка подключения) выводится стандартный Windows-курсор ожидания. После завершения или ошибки исходный курсор восстанавливается. Таймаут задаётся `connection_timeout_seconds`.

## Оформление формы договора

Верхняя часть формы редактирования сохраняет **двухколоночную сетку: восемь пар «подпись — поле»**. Поля расположены в порядке: договор, тип документа, период оказания услуги, **день начала периода, месяц начала периода**, автооплата, сумма, оповещение. Сумма отображается непосредственно в формате N2; никаких дополнительных подсказок между строками сетки не добавляется (подсказка о точности SQL money доступна при наведении на поле суммы).

Даты XDD сгруппированы в отдельные визуально ограниченные блоки с заголовками **«Получение документов»**, **«Оплата по договору»** и **«Отключение услуги»**. Каждый блок содержит направление, количество месяцев, день и собственную подсказку по дате. Все окна используют тематическую иконку «Документ с отметкой»; она же встраивается в Windows EXE.

## Колонки списка — `list_columns`

Каждый элемент массива имеет **ровно шесть полей**:

```json
{
  "field": "PaymentText",
  "title": "Оплата по договору",
  "width": 305,
  "order": 6,
  "sortField": "PaymentCode",
  "visible": true
}
```

- **`field`** — алиас SQL-колонки для отображения в списке. Он обязательно должен присутствовать **в `list_sql`** (регистр букв не учитывается).
- **`title`** — заголовок колонки.
- **`width`** — ширина в пикселях (45–1600).
- **`order`** — уникальное положительное число (1 означает первую колонку); порядок массива JSON роли не играет.
- **`sortField`** — SQL-алиас поля для сортировки по нажатию на заголовок. Может отличаться от `field` и может указывать на скрытое поле результата SQL. Например, отображается текст «Оплата по договору», а сортировка идёт по числовому `PaymentCode`. Повторный щелчок переключает направление сортировки.
- **`visible`** — `true`, если колонка видима; `false`, если скрыта. Для служебных полей `ContractID` и `SearchText` отображение **запрещено независимо от этого флага**; в редакторе колонок переключатель для них недоступен.

**Автосинхронизация с SQL:** при обновлении списка, открытии редактора колонок и сохранении настроек приложение получает алиасы одного `list_sql`. Новые пользовательские алиасы видимы по умолчанию (`visible:true`, `sortField=field`), а `ContractID` и `SearchText` всегда скрыты, а настройки прежних полей остаются неизменными. Если алиас исчез, программа предлагает убрать его настройки; без подтверждения конфигурация остаётся прежней. Если старый `sortField` исчез, он заменяется на `field`, и существующая колонка не теряется. При автоматической записи создаётся `config.json.bak`. SQL-подключение для синхронизации должно быть доступно.

Поля, которые нужны только для сортировки, например `PaymentCode`, уже включены в стандартную конфигурацию как скрытые (`visible:false`), поэтому они не выводятся в новом пустом приложении. В существующем пользовательском `config.json` любой новый обнаруженный SQL-алиас в соответствии с вашим правилом становится **видимым**; при необходимости его можно скрыть через настройки.

`ContractID` и `SearchText` обязательны в SQL-результатах обоих списков, но **никогда не отображаются в таблицах**. `ContractID` используется для выбора/редактирования, `SearchText` — для поиска по словам. Все `field` и `sortField` проверяются по фактическому набору алиасов `list_sql`, даже если SELECT вернул ноль строк. **Встроенных виртуальных столбцов больше нет:** Go ничего не выводит из `ServicePeriod`, `AutoPay` или XDD для списка. Не перечисляйте в `list_columns` поля, отсутствующие в запросах.

В стандартном `config.example.json` `ServicePeriodText`, `AutoPayText`, `DocumentsText`, `PaymentText` и `DisconnectText` формируются в **самом T-SQL** через `CASE`. К примеру, `ServicePeriodText` равен «Один месяц (1)», «Три месяца (3)», «Двенадцать месяцев (12)» или русскому тексту для произвольного количества месяцев. `PaymentText` объясняет код XDD; `PaymentCode` возвращается отдельным числовым полем для корректной сортировки. Можно расширять SQL JOIN-ами и собственными выражениями, но алиасы должны совпадать с настройками колонок.

### Компактное окно контекстного фильтра

Размер окна автоматически зависит от выбранного режима. **Фильтр по введённому значению** открывается в невысоком окне, соответствующем двум строкам условий и кнопкам действий; скрытая таблица уникальных значений больше не оставляет большую пустую область. **Выбор уникальных значений** показывает более высокое окно со списком и галочками. При переключении режимов размеры меняются с сохранением центра окна; пользователь не теряет удобную ширину для операторов и диапазонов. Верхние кнопки сортировки, описание действующего условия и нижние кнопки располагаются с равномерными компактными интервалами. Нужные поля ввода не растягиваются на всю ширину окна.

### Интерфейс фильтра: только используемые поля

Заголовок **«До (для диапазона)»** и поле для второй границы появляются **только** при выборе операторов «Между» или «Вне диапазона». Например, в условии «Сумма между 100 и 500» значение 500 — вторая граница. При обычных сравнениях (равно, содержит, больше и т. д.) дополнительные границы полностью скрыты. Значение для второго условия **ИЛИ** показывается только при выборе второго оператора; для «Выше среднего» и «Ниже среднего» ввод значения не нужен и скрыт.

На обеих вкладках **под таблицей** появляется отдельная многострочная область с **полным текстом применённых фильтров всех колонок**, когда включён хотя бы один фильтр по введённому условию. Например: «Договор: (содержит „Булычев“ ИЛИ содержит „Ник“) И Сумма: больше „1 000“». При наличии также фильтров по уникальным значениям они перечисляются в общем описании с количеством выбранных значений. Когда условий по введённому значению нет, область автоматически скрывается.

Внутри блока **«Фильтр по условию»** добавлена кнопка **«Очистить условие»**. Она немедленно снимает ограничение текущей колонки, сбрасывает оба оператора и их значения, обновляет список договоров и описание фильтров, **не закрывая окно** и не сбрасывая остальные колонки. Это именно немедленное действие: последующее «Отмена» не восстанавливает уже очищенный фильтр. Чтобы задать новое условие, выберите оператор снова.

### Фильтры по условию: текст, число и дата

В Excel-подобном диалоге фильтрации для **обоих списков** добавлен выбор режима:

- **«Выбор уникальных значений»** — прежний список галочек, локальный поиск и подсчёт строк;
- **«Текстовый фильтр»**, **«Числовой фильтр»** или **«Фильтр по дате»** — набор операторов и ввод значений, соответствующие **SQL-типу результата**. Отображаемые суммы \`money\` (и стандартный алиас \`Amount\`) распознаются как числа независимо от N2.

Текст: **равно, не равно, содержит, не содержит, начинается с, заканчивается на** (сравнение без учёта регистра). Числа: **равно/не равно, больше/больше или равно, меньше/меньше или равно, между/вне диапазона, первые N, выше/ниже среднего**. Даты: **равно/не равно, раньше/не позже, позже/не раньше, между/вне периода**. Даты вводятся как \`ДД.ММ.ГГГГ\`, числа принимают и русскую запись \`1 234,56\`.

**Внутри одной колонки допускаются два независимых условия, объединённых через ИЛИ.** Вторая строка необязательна: выберите «— не использовать —», если нужно только одно условие. Обе строки выровнены одинаково: **оператор**, **значение** и **вторая граница**. Последнее поле доступно только для «Между» / «Вне диапазона»; это граница одного условия, **а не отдельная проверка**.

Например, `Договор: (содержит «булычев» ИЛИ начинается с «Контракт»)` **И** `Сумма: больше «5 000»` означает `(A ИЛИ B) И C`. В строке состояния выводится полное человекочитаемое выражение: **ИЛИ** внутри колонки, **И** между колонками.

**Режимы взаимоисключающие в рамках одной колонки.** При выборе условия список галочек становится недоступен; при применении условия прежний отбор уникальных значений этой колонки снимается. Если вернуться к галочкам и нажать «Применить», условие этой колонки снимается. Ограничения **других** колонок остаются действующими и объединяются логическим **И**.

Текущее условие отображается человеческим текстом прямо в диалоге (например, **«Текущий фильтр: содержит „договор“»** или **«Текущий фильтр: между „100“ и „500“»**), а в строке состояния соответствующего списка видны установленные условия с названиями колонок. Столбцы с активными фильтрами отмечаются \`●▾\`.

Условия применяются **локально к уже загруженным из SQL строкам** (в пределах \`list_limit\`), без формирования дополнительных запросов SQL Server. Для числовых условий используются исходные SQL-значения, а не округлённый текст N2. Значения других колонок в раскрывающемся фильтре продолжают зависеть от всех действующих ограничений. В режиме «Первые N» и «Выше/ниже среднего» величина порога рассчитывается по доступным загруженным числовым значениям.

### Excel-подобная контекстная фильтрация

**В обеих таблицах подпись поиска одинаковая — «Поиск по договору:».** **В обеих таблицах каждый заголовок показывает стрелку `▾`**. Нажмите на заголовок, чтобы открыть меню фильтра. В нём доступны:
- сортировка по возрастанию и убыванию (для основного списка используется `sortField`);
- локальный поиск по уникальным значениям, включая пустые (`(Пустые)`): сравнение по подстроке, без учёта регистра (`Contains` / `LIKE '%слово%'`), выполняется по **Enter или после потери фокуса**; введённый текст не отправляется в SQL Server;
- галочки выбора конкретных значений с подсчётом строк, кнопки «Выбрать всё» и «Снять всё»; массовые изменения сразу перерисовывают галочки без необходимости проводить по ним мышью. При активном поиске среди значений эти две кнопки действуют только на найденные значения, остальные отметки сохраняются;
- «Применить», «Сбросить колонку» и «Сбросить все» (фильтры данной вкладки).

При активном фильтре заголовок помечается `●▾`. Окно фильтра открывается после завершения обработки клика по заголовку, поэтому кнопки сортировки реагируют на первый щелчок. **Фильтры нескольких колонок объединяются через AND** и применяются к **уже загруженным строкам**. При открытии фильтра определённой колонки набор доступных значений и их количество вычисляются **с учётом всех остальных активных фильтров**, но без ограничения по самой открытой колонке (так её выбор можно изменить). Сброс фильтра одной колонки не сбрасывает остальные. Фильтрация выполняется только по строкам, уже загруженным текущим SQL-запросом в пределах `list_limit`. Они не меняют пользовательский SQL, не отправляют дополнительных запросов в базу и не фильтруют записи за пределами загруженной выборки. При обновлении списка фильтры сохраняются и применяются повторно к новым строкам. Фильтры на двух вкладках независимы.

Сортировка из меню заголовка меняет **только порядок строк** уже загруженной выборки, не переставляя колонки. Перетаскивание заголовков колонок в обоих списках **отключено**: порядок основного списка меняется в редакторе `list_columns` (поле `order`), а порядок второго определяется итоговым `SELECT`. Это исключает несохранённые перестановки при перетаскивании.

**Первоначальную сортировку на SQL Server до `TOP (@limit)`** определяют параметры `list_order_by` и `without_parameters_order_by`; сортировка на экране не добавляет записи, не попавшие в серверную выборку.

Для старого `config.json` запрос `without_parameters_sql` заполняется автоматически примером, а поля `order`, `sortField` и `visible` заполняются автоматически: порядком массива, `field` и `true` соответственно. **Старые виртуальные поля требуют правки SQL:** добавьте вычисление соответствующих алиасов в свои запросы, ориентируясь на новый `config.example.json`; иначе программа предложит удалить отсутствующие поля из `list_columns`. Пользовательские SQL-запросы при обновлении автоматически не переписываются.

## XDD — правила дат

Начало услуги 07.01, период 3 месяца:

| Код SQL `int` | Смысл | Примерный срок |
|---|---|---|
| `9` (`009`) | 9-е число от месяца начала | 09.01 |
| `120` | 20-е число со смещением +1 | 20.02 |
| `-120` | 20-е число со смещением −1 | 20.12 предыдущего года |
| `-6` (`-006`) | 6-е число до начала | 06.01 |
| `306` | не ранее 07.04, ближайшее 6-е | 06.05 |
| `320` | не ранее 07.04, ближайшее 20-е | 20.04 |
| `420` | 20-е со смещением +4 | 20.05 |
| `99` (`099`) | конец января | 31.01 |
| `199` | конец февраля | 28 или 29.02 |

Минус и плюс (относительно начала периода) применяются ко всем трём полям независимо от периода услуги. DD=99 означает последний календарный день соответствующего месяца.
